# Naval Battles

Минимальный сетевой «Морской бой» для двух игроков на Unity 6 и Photon Fusion 2. Для локальной демонстрации используются три обычных процесса Unity: основной проект с сервером и два клона ParrelSync с клиентами. Процессы взаимодействуют только сериализованными прикладными сообщениями.

## Как запустить

1. Открыть проект в Unity `6000.3.15f1`.
2. Через `ParrelSync → Clones Manager` создать и открыть два клона проекта. У каждого экземпляра должны быть собственные доступные для записи `Library` и `UserSettings`.
3. В каждом Editor открыть `Naval Battles → Instance Role`: в основном проекте выбрать `Server`, в обоих клонах — `Client`.
4. В Fusion Hub проверить, что в `PhotonAppSettings` указан AppId отдельного Photon Fusion приложения.
5. Открыть `Assets/NavalBattles/Scenes/Game.unity` во всех трёх Editor и нажать Play сначала на сервере, затем на клиентах.
6. Дождаться подключения обоих клиентов. Сервер назначит `Игрока 1` и `Игрока 2` по порядку входа; каждый клиент независимо показывает только `Вы` и `Соперник`.
7. Стрелять по полю соперника. В каждом клиентском окне показаны оба поля, состав флота, состояние соединения, ход, таймер и ожидающий ответа выстрел.
8. В `Network Debug` можно для локального клиента задать delay, jitter, loss и duplicate, применить профиль, разорвать/восстановить связь или пересоздать клиент.
9. `Show network log` включает ограниченный по размеру прокручиваемый лог с направлением, статусом доставки, типом протокольного сообщения и размером пакета. При появлении записи лог автоматически прокручивается вниз.

В Build Settings `Game.unity` имеет индекс 0, а пустая сетевая сцена `NetworkPeer.unity` — индекс 1. Дополнительная ручная настройка сцены не требуется.

Роль каждого Editor хранится локально в `UserSettings/NavalBattlesInstance.json` и не передаётся клонам. Для клиента там же атомарно сохраняются стабильный `clientId` и следующий `commandId`: они переживают restart сцены, полное пересоздание клиента и повторный запуск Editor. Флаги `-server` и `-client` имеют приоритет над локальным файлом; standalone без флага запускается как Client. Одновременные `-server` и `-client` считаются ошибкой конфигурации.

AppId не даёт доступа к панели Photon, но посторонний пользователь может расходовать квоту приложения. Для публичного репозитория следует использовать только отдельное временное приложение и удалить или отключить его после проверки тестового задания.

## Архитектура — 12 строк

1. `Domain` — чистые правила поля, флота и матча без Unity и Photon.
2. `Protocol` — контракты сообщений и заменяемый `IProtocolSerializer`.
3. `Transport` — доставка байтов, детерминированная симуляция сети и транспортная диагностика.
4. `Server` — единственный источник истины, проверка команд и персональные snapshot.
5. `Client` — состояние соединения, pending-команда, retry, heartbeat и применение snapshot.
6. Клиентская сборка не ссылается на серверную; обе зависят от абстракций транспорта.
7. `UnityIntegration/Fusion` адаптирует reliable data Fusion к `IMessageTransport`.
8. Основной Editor и два клона ParrelSync с независимыми `Library`/`UserSettings` запускают один Server runner и два Client runner.
9. Каждый `GameBootstrap` собирает и завершает ровно одну server- или client-composition.
10. `GameSceneController` владеет Unity lifetime, пересозданием клиента и reload сцены.
11. UI построен по MVP: MonoBehaviour View, обычный C# Presenter и плоские модели представления.
12. EditMode проверяет чистую логику, PlayMode — реальную топологию Fusion и lifecycle сцены.

## Протокол

Каждый пакет содержит версию протокола, тип сообщения, `messageId`, стабильный `clientId` для клиентских сообщений, длину payload и типизированный бинарный payload. Текущая версия wire-format — 2; несовместимая версия отклоняется до чтения payload. Реализация — `BinaryProtocolSerializer`; потребители зависят от `IProtocolSerializer`, поэтому формат можно заменить, например, на Protobuf без изменения клиента и сервера.

| Направление | Сообщение | Назначение |
| --- | --- | --- |
| Client → Server | `ConnectRequest` | Первое подключение стабильного `clientId`. |
| Client → Server | `ResumeRequest` | Возврат после разрыва с известной клиенту `revision`. |
| Client → Server | `FireRequest` | `commandId`, идентификатор хода и индекс клетки. |
| Client → Server | `StateRequest` | Запрос актуального snapshot после расхождения или потери ответа. |
| Client → Server | `HeartbeatRequest` | Проверка живости прикладного канала. |
| Server → Client | `SessionAccepted` | Назначенное место игрока и публичные правила матча. |
| Server → Client | `FireResult` | Авторитетный результат или статус конкретной команды. |
| Server → Client | `StateSnapshot` | Персональная проекция матча с монотонной `revision`. |
| Server → Client | `HeartbeatResponse` | Подтверждение живости, серверное время и корреляция по `messageId` запроса. |
| Server → Client | `RequestRejected` | Причина отклонения команды. |

Snapshot собственного поля содержит корабли и входящие выстрелы. Snapshot поля соперника содержит только уже известные результаты выстрелов; скрытое расположение кораблей по сети не передаётся.

## Правила и отображение

- Сервер размещает флот 3/2/2/1 на поле 6×6; разные корабли не касаются ни сторонами, ни углами.
- После принятого выстрела ход всегда переходит сопернику, включая попадание.
- После потопления свободные клетки контура автоматически становятся известными промахами и приходят клиентам в обычном snapshot.
- Сервер обрабатывает 15-секундный deadline раньше команды, пришедшей в тот же момент или позже.
- На своём поле клиент видит корабли и выстрелы противника, на чужом — только результаты собственных выстрелов.

## Разрыв связи и гарантии

«Разорвать» закрывает прикладной gate: транспорт не сообщает клиенту о разрыве, а сообщения перестают доходить. Heartbeat timeout переводит клиента в `Disconnected`. После «Подключить» gate открывается, клиент отправляет `ResumeRequest`, сервер находит прежнюю сессию по стабильному `clientId` и возвращает полный актуальный snapshot. При полном пересоздании новый Fusion `PlayerRef` привязывается к тому же месту игрока.

- Каждый выстрел получает монотонный `commandId`; retry повторяет тот же идентификатор.
- Сервер кэширует результат обработанной команды и не применяет дубликат повторно.
- Пока ответ на выстрел не получен, клиент не отправляет второй выстрел.
- Сервер повторно проверяет активного игрока, ход, клетку и deadline независимо от UI.
- Snapshot имеет монотонную `revision`; старое сообщение не может откатить состояние.
- Вместе с heartbeat подключённый клиент периодически отправляет `StateRequest`, поэтому потерянный финальный snapshot будет получен повторно даже без следующих игровых изменений.
- До `SessionAccepted` один и тот же сериализованный `ConnectRequest`/`ResumeRequest` повторяется по retry interval.
- Причина прямого отказа (`WrongTurn`, `TurnExpired` и другие) сохраняется клиентом и показывается в его панели; после восстановления неизвестный исход показывается как общий отказ.
- При `serverTime >= deadline` timeout обрабатывается раньше пришедшей команды.
- Клиент коррелирует heartbeat по `messageId`, оценивает смещение часов через midpoint RTT и переводит серверный deadline в локальную монотонную шкалу; задержанный snapshot не запускает новый полный интервал.
- Устаревшие, неизвестные и оставшиеся от предыдущего подключения time samples игнорируются.
- Матч не ставится на паузу при отсутствии игрока: его ходы продолжают завершаться по timeout.
- Перед reload сцены Presenter отписываются, lifetime отменяется, runner завершаются, и только затем загружается новая сцена.

## Принятые решения и упрощения

- Реализован один матч на два места игрока; lobby, matchmaking UI и несколько одновременных матчей не входят в объём.
- Состояние хранится в памяти. Перезапуск сервера начинает новый матч; восстановление после restart сервера не реализовано.
- Плохая сеть моделируется над сериализованными прикладными сообщениями, поэтому профиль воспроизводим и не ломает внутренний протокол Fusion.
- Сервер использует детерминированную случайную расстановку по seed. В production seed следовало бы получать из криптографически стойкого источника и сохранять вместе с матчем.
- UI намеренно собран на UGUI без анимаций и художественных assets: оцениваются архитектура и сетевое поведение.
- Сетевой лог ограничен последними 4000 символами, чтобы длительная сессия не раздувала UI.
- При restart сцены bootstrap дожидается незавершённого recreation, затем завершает созданный client runner; этот overlap закреплён PlayMode regression test.
- Использована ручная constructor injection. VContainer, R3 и MessagePipe не добавлены: для одного composition root они увеличили бы количество инфраструктурного кода.
- ECS/DOTS не используется; data-oriented часть представлена плоскими массивами и компактными значениями состояния.

## Тесты

Открыть `Window → General → Test Runner`:

- EditMode — правила, расстановка, матч, сериализация, server/client recovery, симуляция транспорта и Presenter;
- PlayMode — реальные Fusion peers, обмен в обе стороны, silent reconnect, recreation, запуск и restart сцены.

Последние сохранённые полные прогоны:

- EditMode: 101/101 — `TestResults-client-identity-editmode-final.xml`;
- PlayMode: 6/6 — `TestResults-client-identity-playmode.xml`.

Batchmode-команды приведены в `docs/superpowers/plans/2026-09-25-naval-battles.md`. Для PlayMode нужен доступ к Photon Cloud и действующий тестовый AppId.

## Фактическое время и отклонения

Фактически ушло около 21 часа активной разработки и проверки.

- Больше плана заняли lifecycle Fusion runner, восстановление с новым `PlayerRef` и live PlayMode-прогоны.
- После добавления `Game.unity` первой в Build Settings старые tests продолжали использовать индекс 0 как сетевую сцену. Полный прогон обнаружил рекурсивный запуск второго server; tests переведены на `NetworkPeer.unity` с индексом 1.
- Генерация сцены сначала сохранила пустые ссылки на недавно созданные config assets, а legacy input module конфликтовал с новым Input System. Обе проблемы обнаружены live scene tests.
- Иерархия отдельных DTO-классов для каждого сообщения оказалась тяжелее исходной задачи; её заменил компактный union с именованными фабриками, сохранив отдельную абстракцию сериализатора.
- Из дополнительных возможностей намеренно не сделаны сохранение матча и восстановление сервера: при ограничении по времени приоритет отдан exactly-once выстрелам, reconnect и тестам.
- Финальный независимый review обнаружил retry handshake, монотонность `SessionAccepted`, восстановление потерянного финального snapshot, отображение отказа и cleanup runner при ошибке старта. Все пять сценариев закреплены regression tests.
- Изначальный пересчёт клиентского таймера по времени получения snapshot повторно добавлял сетевую задержку. Реализация заменена коррелированными heartbeat samples и оценкой смещения часов через midpoint RTT.
- Идентичность клиента сначала жила только в runtime. Теперь `clientId` и следующий `commandId` сохраняются в локальном `UserSettings`, поэтому повторный запуск Editor корректно возвращает игрока в прежнюю серверную сессию.
