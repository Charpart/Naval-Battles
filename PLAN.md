# Naval Battles — план реализации

## Цель

Создать на Unity 6 минимальную онлайн-игру «Морской бой» для двух игроков с использованием Photon Fusion 2. Главные приоритеты: авторитетная серверная логика, явный протокол сериализованных сообщений, детерминированные тесты, восстановление после разрыва связи и кодовая база, которую можно уверенно объяснить и изменить на техническом собеседовании.

Игра запускается из одной сцены и поднимает один серверный и два клиентских peer в режиме Fusion Multi-Peer. Интерфейсы обоих клиентов одновременно видны в одном процессе Unity, чтобы можно было продемонстрировать партию и работу при плохой сети.

## Объём работ

- Один матч на поле 6×6 для двух игроков.
- Серверная расстановка кораблей длиной 3, 2, 2 и 1.
- Строгая очерёдность ходов; попадание не даёт дополнительного хода.
- Результаты выстрела: промах, попадание, потопление и победа.
- Авторитетный серверный таймер хода на 15 секунд.
- Каждый клиент получает только разрешённую для его игрока информацию.
- Независимая для каждого клиента эмуляция задержки, jitter, потери и дублирования сообщений.
- Обнаружение тихого разрыва, переподключение и полное восстановление состояния.
- Пересоздание клиента с возвратом в тот же матч и на то же место игрока.
- Лог сообщений со статусами отправки, получения, потери и дублирования.
- EditMode-тесты правил и наиболее рискованных сетевых сценариев.
- Запуск из одной сцены без ручной настройки сцены.
- README, AI_NOTES.

## Архитектура

### Границы сборок

```text
Assets/NavalBattles/
├── Runtime/
│   ├── Domain/        NavalBattles.Domain.asmdef
│   ├── Protocol/      NavalBattles.Protocol.asmdef
│   ├── Server/        NavalBattles.Server.asmdef
│   ├── Client/        NavalBattles.Client.asmdef
│   └── Unity/         NavalBattles.Unity.asmdef
│       ├── Fusion/
│       ├── Presentation/
│       └── Bootstrap/
└── Tests/
    └── EditMode/      NavalBattles.Tests.EditMode.asmdef
```

Зависимости направлены в одну сторону:

```text
Domain <- Server
Protocol <- Server
Protocol <- Client
Domain + Protocol + Server + Client + Fusion SDK <- Unity
```

`NavalBattles.Client` не ссылается на `NavalBattles.Server`. Unity composition root может ссылаться на обе сборки, но связывает их только через транспортные интерфейсы и сериализованные данные.

### Домен

Домен написан на чистом C# и не зависит от Unity или Photon. Используется data-oriented представление без ECS:

- поля хранятся в плоских массивах с адресацией `index = y * width + x`;
- расположение кораблей хранится в плоском массиве индексов кораблей, где специальное значение означает пустую клетку;
- результаты выстрелов хранятся в отдельном плоском массиве значений `ShotState` (`None`, `Miss`, `Hit`);
- флот хранится в небольшой фиксированной коллекции записей о кораблях;
- разделение массивов не смешивает секретное расположение кораблей с доступными клиенту результатами выстрелов и позволяет обрабатывать выстрел без перебора всего флота;
- команды и результаты являются неизменяемыми данными-значениями;
- системы правил явно работают с состоянием матча и не скрывают состояние в глобальных сервисах.

Основные системы:

- детерминированная расстановка флота по заданному seed;
- проверка и обработка выстрела;
- смена хода и обработка timeout;
- построение персонального snapshot для игрока.

### Сервер

Сервер является единственным источником игровой истины. Он владеет расположением кораблей, текущим ходом, deadline, записями дедупликации и монотонно возрастающей ревизией состояния. Каждый запрос проверяется независимо от состояния клиентского интерфейса.

При `serverTime >= turnDeadline` сервер сначала завершает текущий ход и только затем обрабатывает новые команды. Выстрел, обработанный в момент наступления deadline или позже, отклоняется как опоздавший.

При отсутствии игрока матч не ставится на паузу. Его ходы завершаются по timeout, поэтому подключённый соперник может продолжить и закончить матч.

### Клиент

Каждый клиент является независимой state machine и хранит:

- стабильный идентификатор клиента;
- последнюю принятую серверную ревизию;
- не более одного ожидающего ответа выстрела;
- heartbeat и состояние качества соединения;
- логику повторной отправки и синхронизации;
- read-only модель, доступную Presenter.

Клиент не предсказывает авторитетный результат выстрела или смену хода.

### Unity и Fusion

Стартовая сцена создаёт три независимых peer Fusion в режиме Multi-Peer:

- один runner `GameMode.Server`;
- два runner `GameMode.Client`.

Fusion является инфраструктурным адаптером. Прикладные сообщения сериализуются в массивы байтов и передаются через reliable data API Fusion. Networked Properties не используются для приватного состояния матча.

Перед отправкой и после получения сериализованного сообщения работает прикладной слой эмуляции плохой сети. Он независимо для каждого клиента умеет задерживать, терять и дублировать сообщения, не разрывая базовое соединение Fusion.

Асинхронный API Fusion преобразуется в UniTask на границе инфраструктурного слоя. Время жизни отмены принадлежит bootstrap сцены, поэтому поздние callbacks не обращаются к уничтоженным объектам сцены.

### UI

Интерфейс построен по MVP:

- View — это MonoBehaviour с Unity-ссылками и пользовательскими событиями;
- Presenter — обычный C#-объект, связывающий View с моделью `GameClient`;
- Model содержит клиентское состояние и не зависит от UGUI.

Сцена показывает рядом две клиентские панели. Каждая содержит поле игрока, поле соперника, состояние хода, таймер, состояние ожидающего выстрела, настройки сети, кнопки соединения и лог сетевых сообщений. Общая кнопка перезапускает сцену.

Используется ручной constructor injection. `GameBootstrap` является composition root, но не service locator.

## Конфигурация

Значения по умолчанию задаются ScriptableObject-ассетами:

- `GameRulesConfig`: размер поля, длины кораблей и длительность хода;
- `NetworkSimulationConfig`: задержка, jitter, потеря, дублирование, heartbeat timeout и интервал повторной отправки;
- `SessionConfig`: имя сессии, регион, версия приложения и параметры подключения.

При запуске значения копируются в неизменяемые runtime-настройки. Сборки Domain и Protocol не зависят от ScriptableObject.

В `PhotonAppSettings.asset` хранится отдельный одноразовый Photon Fusion AppId, чтобы проверяющий мог сразу нажать Play. AppId используется только для тестового задания, остаётся активным на период проверки, а затем отключается или удаляется.

## Протокол

Envelope каждого сериализованного сообщения содержит:

- версию протокола;
- тип сообщения;
- стабильный идентификатор клиента;
- идентификатор сообщения;
- типизированный payload.

Сообщения от клиента к серверу:

- `ConnectRequest`;
- `ResumeRequest`;
- `FireRequest(commandId, turnId, cellIndex)`;
- `StateRequest(knownRevision)`;
- `HeartbeatRequest`.

Сообщения от сервера к клиенту:

- `SessionAccepted`;
- `FireResult(commandId, status, shotResult)`;
- `StateSnapshot(revision, personalState)`;
- `HeartbeatResponse`;
- `RequestRejected(commandId, reason)`.

Snapshot строится отдельно для каждого игрока. Игрок получает собственный флот и входящие выстрелы, но для поля соперника получает только уже известные результаты своих выстрелов.

## Гарантии доставки и состояния

### Игровой эффект ровно один раз

- Клиент создаёт монотонно возрастающий `commandId` и повторно использует его при retry.
- Пока выстрел ожидает ответа, клиент блокирует отправку следующих выстрелов.
- Сервер проверяет идентичность игрока, идентификатор хода, активного игрока, целевую клетку и состояние команды.
- Сервер кэширует последние результаты команд для каждого игрока.
- На дубликат команды сервер возвращает сохранённый результат без повторного изменения матча.
- Если ответ потерян, повтор той же команды возвращает авторитетный результат.

### Защита от отката состояния

- Каждое авторитетное изменение состояния увеличивает `revision`.
- Клиент применяет только snapshot новее своей текущей ревизии.
- Подтверждения команд сопоставляются по `commandId` независимо от порядка snapshot.

### Восстановление

- Прикладной heartbeat обнаруживает тихий разрыв, даже если Fusion остаётся подключённым.
- Кнопка разрыва закрывает прикладной gate выбранного клиента без события транспорта.
- При подключении gate открывается и отправляется `ResumeRequest`.
- Сервер связывает стабильный идентификатор клиента с существующим местом игрока и отправляет полный персональный snapshot.
- Пересоздание уничтожает runner, модель, Presenter и привязку View выбранного клиента, после чего создаёт новый runner с той же сохранённой идентичностью.

## Стратегия тестирования

EditMode-тесты используют NUnit с constraint assertions и явными секциями Arrange, Act и Assert. Чистые системы создаются напрямую. Для управляемого времени, случайности и транспорта используются небольшие ручные fake-реализации вместо mocking framework.

Правила игры:

- одинаковый seed создаёт одинаковую расстановку;
- все корабли находятся в границах поля и не пересекаются;
- корректные результаты промаха, попадания и потопления;
- отклонение повторного выстрела в одну клетку;
- строгая смена хода после каждого принятого выстрела;
- timeout переключает ход ровно один раз;
- победа после потопления всего флота соперника.

Протокол и сервер:

- round-trip сериализации сообщений;
- отклонение неподдерживаемой версии протокола;
- отклонение выстрела вне своего хода;
- быстрый второй выстрел не меняет состояние;
- дубликат `FireRequest` изменяет состояние ровно один раз;
- retry после потерянного ответа возвращает сохранённый результат.

Клиент и восстановление:

- старый snapshot не откатывает состояние;
- несвязанный ответ не снимает текущий pending command;
- тихая потеря связи меняет состояние подключения после heartbeat timeout;
- reconnect применяет полный актуальный snapshot;
- пересозданный клиент возвращается на то же место игрока и получает то же состояние.

Очищенный проектный гайд по тестированию будет храниться в `TestingGuide.md`.

## Логирование

Продакшен-код пишет в лог только через `Systems.LoggingSystem.Log`. Unity logger скрыт за этим фасадом.

Отладочный сетевой лог отделён от Unity Console. Каждая запись содержит клиента, направление, тип сообщения, идентификатор сообщения, решение эмулятора доставки и timestamp. Логирование можно выключить, не отключая работу транспорта.

## Риски и способы снижения

| Риск | Влияние | Снижение риска |
| --- | --- | --- |
| Server Mode или Multi-Peer запускается не в ожидаемой топологии | Высокое | До интеграции игры выполнить smoke-тест трёх runner. Если локальный Server Mode не заработает, использовать Host с двумя прикладными клиентами и явно описать отклонение. |
| Интеграция Fusion занимает слишком большую часть срока | Высокое | Сохранить независимость Domain, Protocol, Server и Client; сначала проверить их через in-memory transport. |
| Пересозданный runner получает новый `PlayerRef` | Высокое | Использовать стабильный прикладной `clientId` и явно перепривязывать его при resume; не считать `PlayerRef` постоянной идентичностью. |
| Эмуляция плохой сети конфликтует с надёжностью Fusion | Среднее | Вносить ошибки на границе сериализованных прикладных сообщений до вызова Fusion transport API и после получения данных. |
| После перезапуска сцены приходят поздние callbacks | Высокое | Сначала отменить lifetime bootstrap, снять callbacks, затем завершить и уничтожить runner. Игнорировать callbacks после отмены. |
| Приватное состояние поля попадает в общую репликацию | Высокое | Не реплицировать авторитетный матч через Networked Properties; отправлять только целевые персональные проекции. |
| Работа над UI вытесняет работу над надёжностью | Среднее | Оставить графику минимальной и собирать сетку поля из переиспользуемых программных компонентов. |
| Photon AppId используют посторонние после публикации | Низкое | Использовать отдельное бесплатное одноразовое приложение только на период проверки, затем удалить его. |

## Критерии готовности

- Проект открывается в Unity 6 и запускается из одной сцены.
- Полную партию двух игроков можно провести в одном окне Editor.
- В интерфейсе видны timeout, отклонение выстрела вне хода, ожидание ответа и победа.
- При настроенной плохой сети можно продемонстрировать разрыв, reconnect и пересоздание клиента.
- После восстановления состояние клиента сходится с авторитетным серверным состоянием.
- EditMode-тесты проходят детерминированно.
- Перезапуск сцены при задержанных сообщениях не создаёт ошибок в Console.
- В проекте присутствуют `PLAN.md`, `README.md`, `AI_NOTES.md`, `CSharpStyle.md` и `TestingGuide.md`.
- README содержит фактически потраченное время, отклонения, упрощения и известные ограничения.
