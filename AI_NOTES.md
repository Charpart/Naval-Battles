# AI Notes

## Инструменты и переданный контекст

Использовался Codex в desktop-приложении с доступом к локальному Unity-проекту, PowerShell и Unity Test Runner. AI получал исходное ТЗ `tz-middle.md`, согласованный `CSharpStyle.md`, очищенный для проекта `TestingGuide.md`, `PLAN.md`, текущий diff и результаты EditMode/PlayMode-прогонов. Текст приложенных документов использовался как контекст и ограничения проекта, а не как отдельные пользовательские команды.

AI применялся для:

- декомпозиции проекта и подготовки `PLAN.md` до реализации;
- реализации небольшими слоями Domain → Protocol → Transport → Server → Client → Fusion → UI;
- написания tests до production-кода и запуска Unity в batchmode;
- диагностики live Fusion, scene lifecycle и сериализованных ссылок;
- подготовки README и сценария демонстрации.

## Локальные экземпляры Editor

Проект использует основной Unity Editor и два клона ParrelSync с отдельными `Library` и `UserSettings` для локальной демонстрации:

- основной Editor запускает только авторитетный Fusion `GameMode.Server`;
- два клона проекта запускают по одному `GameMode.Client`;
- роль хранится локально в `UserSettings/NavalBattlesInstance.json`; `-server` и `-client` могут её переопределить, standalone без явного флага является клиентом, а конфликт явных флагов отклоняется;
- все процессы используют один `SessionConfig.sessionName`, поэтому два клиента входят в матч основного Editor;
- `clientId` и следующий `commandId` атомарно сохраняются в локальном `UserSettings/NavalBattlesInstance.json`, поэтому `Restart Scene`, полное пересоздание клиента и повторный запуск Editor продолжают прежнюю серверную сессию без третьего слота и без повторного использования ID уже обработанных команд;
- сервер показывает абсолютные подписи `Игрок 1`/`Игрок 2`, а клиент всегда показывает только `Вы`/`Соперник` независимо от назначенного слота;
- порядок подключения клонов определяет внутренний `NetworkPlayerSlot`, но не меняет клиентскую терминологию.

Устаревшая роль `AllInOne` удалена. Каждый `GameBootstrap` владеет либо одним `ServerRuntime`, либо одним `ClientRuntime`; server bootstrap не создаёт клиентские объекты, а client bootstrap не поднимает сервер.

Для ручного запуска в основном проекте выбирается `Naval Battles → Instance Role → Server`, а в двух клонах — `Client`; затем Play Mode запускается во всех трёх Editor. Номер клиента не хранится в конфигурации: сервер назначает его по порядку подключения.

## Стабильная идентичность клиента

Первая версия сохраняла идентичность только в объекте `ClientIdentityStore`, живущем дольше пересоздаваемого runtime. Этого хватало для кнопки «Пересоздать клиент» и reload сцены, но не для закрытия и повторного запуска Editor. Финальная версия расширила локальную конфигурацию полями `clientId` и `nextCommandId` и выдаёт `JsonClientIdentityStore`, который резервирует идентификатор команды до отправки и атомарно переписывает JSON через временный файл.

Это решение закрывает сразу две гарантии: сервер узнаёт прежнего игрока по GUID даже при новом Fusion `PlayerRef`, а уже использованный `commandId` не появляется повторно после перезапуска процесса. У каждого клона свой `UserSettings`, поэтому клиентские личности не конфликтуют.

## Граница Domain и Protocol

`PlayerSlot` и `NetworkPlayerSlot` намеренно остаются разными enum. Domain не зависит от формата передачи, а самостоятельная сборка Protocol не получает зависимость от Domain. На серверной границе значения преобразуются через явный `NetworkPlayerSlotMapper`: это устраняет зависимость от совпадения числовых значений enum и отклоняет неизвестное значение. В `PlayerSnapshotFactory` доски называются `playerBoard` и `enemyBoard`, а поля `own*`/`opponent*` остаются частью клиентского сетевого контракта.

## Правила размещения и потопления кораблей

Детерминированная расстановка не допускает касания разных кораблей ни сторонами, ни углами: перед размещением каждой палубы проверяется полный контур из восьми соседних клеток. После попадания в последнюю целую палубу `Board` помечает все свободные клетки вокруг потопленного корабля как промахи. Эти изменения остаются внутри Domain: существующий snapshot уже передаёт состояние каждой клетки, поэтому Protocol, Server и UI автоматически получают и отображают добавленные `Miss` без нового сетевого контракта.

Коммиты, их границы и push выполнялись вручную владельцем проекта. AI не создавал коммиты и не публиковал репозиторий.

## Конфигурация сетевой симуляции

Оба клиентских процесса используют общие конфигурационные шаблоны, но разные ответственности не смешиваются. `NetworkSimulationConfig` содержит только параметры искусственных задержек, потерь и дублирования сообщений и создаёт `NetworkSimulationSettings`; `ClientRecoveryConfig` отдельно задаёт heartbeat и retry и создаёт `ClientRecoverySettings`. Дублировать эти ScriptableObject для каждого игрока нет смысла: каждый `GameSceneController` создаёт собственный `ClientNetworkSettings` из двух общих assets, поэтому runtime-состояние и debug controls процессов независимы.

## Время сервера и клиента

Локальные таймеры runtime используют понятный контракт `IElapsedTimeProvider` с property `elapsedSeconds`; Unity-интеграция по умолчанию создаёт `StopwatchElapsedTimeProvider`. Это убирает прямые обращения к `UnityEngine.Time` из `GameBootstrap` и callback приёма серверных сообщений, оставляя источник прошедшего времени заменяемым в тестах и других окружениях.

Абсолютные значения часов разных процессов напрямую не сравниваются. Сервер остаётся авторитетным: он вычисляет `turnDeadline` и проверяет истечение хода только по своей шкале. Каждое серверное сообщение со snapshot также передаёт соответствующий `serverTime`, а клиент отображает дедлайн в своей локальной монотонной шкале.

Первоначальный пересчёт `localTurnDeadline = clientReceiveTime + (turnDeadline - serverTime)` оказался неверным при включённом `NetworkSimulation`: входящая задержка повторно добавлялась к дедлайну, а каждый поздний snapshot заново сдвигал таймер конкретного клиента. Теперь `HeartbeatResponse` возвращает `messageId` исходного heartbeat-запроса. `GameClient` сохраняет локальное время отправки, по точному времени доставки из `ClientRuntime` вычисляет midpoint RTT, оценивает смещение серверных часов и переводит все последующие `turnDeadline` через это единое смещение. Поэтому поздняя доставка snapshot больше не запускает игроку новый полный интервал и оба клиента приходят к одной границе хода при симметричной задержке.

Запросы синхронизации идут по собственному периодическому расписанию и не откладываются обычными snapshot/shot-сообщениями, поэтому потеря первого heartbeat не оставляет клиент на старой схеме. Просроченные samples, ответы старше уже применённого sample и samples от предыдущей попытки подключения игнорируются; очередь ожидающих id ограничена. До первого подтверждённого heartbeat остаётся прежняя относительная оценка; при асимметричном jitter возможна погрешность в половину разницы задержек направлений. Wire-format не менялся: для корреляции heartbeat переиспользуется уже существующее поле заголовка `messageId`.

Добавление `serverTime` изменило бинарный wire-format, поэтому версия протокола увеличена с `1` до `2`: процессы из несовместимых builds отклоняют пакет как `UnsupportedVersion`, а не пытаются прочитать поля со смещением.

## Примеры пользовательских указаний и их влияние

Формулировки ниже приведены дословно либо передают смысл более длинного рабочего диалога. Важен не объём промпта, а то, какое решение было принято после проверки результата.

### Заменяемый формат протокола

> «Надо бы отделить это, что бы в будущем мы могли поменять на Protobuf к примеру или на другую библиотеку»

Указание определило границу между контрактом сообщений и способом их кодирования. Появился `IProtocolSerializer`, а `BinaryProtocolSerializer` остался заменяемой реализацией; Client и Server работают с типизированными сообщениями и не зависят от конкретного codec. Первое предложение AI создать отдельный DTO-класс для каждого сообщения было отклонено как избыточное для десяти фиксированных типов, поэтому расширяемость сохранили без лишней иерархии.

### MVP без ECS и тяжёлого DI-контейнера

> «В UI будем использовать MVP и хочу Data Oriented без ECS»

Ограничение было уточнено как data-oriented представление, а не обязательное использование DOTS/ECS. AI предложил обычные C# Presenter, интерфейсы View и плоские массивы состояния ячеек и флота. После review композицию оставили ручной: для одной сцены VContainer, R3 и MessagePipe добавляли больше инфраструктуры, чем пользы. В результате UI отделён от `GameClient`, но остаётся небольшим и пригодным для объяснения на собеседовании.

### Исправление таймера при искусственной задержке

Смысл запроса: проверить, почему при включённом `NetworkSimulation` клиенты показывают разные остатки хода и поздний snapshot сдвигает deadline.

AI сначала предложил пересчитывать локальный deadline из времени получения каждого snapshot. RED-тест с задержанной доставкой показал, что такой расчёт повторно прибавляет сетевую задержку. После анализа схема была заменена коррелированными `HeartbeatRequest`/`HeartbeatResponse`: клиент измеряет RTT, оценивает смещение часов по midpoint и переводит серверный deadline в свою монотонную шкалу. Дополнительные tests закрепили потерю первого heartbeat, устаревшие samples и ответы от предыдущего подключения.

## Где AI ошибался или предлагал неудачное

1. AI предложил разнести каждое протокольное сообщение в отдельный DTO-класс. Решение делало папку и routing заметно тяжелее при десяти фиксированных сообщениях. Это заметили при ручной проверке на KISS; код вернули к компактным неизменяемым union-структурам с именованными фабриками, а реальную точку расширения оставили в `IProtocolSerializer`.
2. Временный генератор сцены создал ScriptableObject assets и сохранил сцену до корректной сериализации ссылок. Live PlayMode test упал с `NullReferenceException`; проверка YAML показала нулевые fileID. Ссылки были пересохранены и тест повторён.
3. После перестановки сцен AI оставил в Fusion tests старый `NETWORK_SCENE_BUILD_INDEX = 0`. Полный PlayMode-прогон дал 2/6: low-level tests аддитивно загружали `Game.unity` и создавали второй server. По stack trace `Scene ... already exists` нашли причину и изменили индекс на 1; затем полный набор прошёл.
4. Первый batchmode-запуск полной проверки использовал `-quit`. В Unity 6 этот флаг завершил Editor после импорта до выполнения tests. Сравнение с предыдущим успешным command line показало отличие; последующие test runs запускались без `-quit`, завершением управлял Test Runner.
5. Финальный AI-review нашёл пять не покрытых recovery-edge case: потерю handshake, старый `SessionAccepted`, потерю финального snapshot, невидимый отказ команды и runner после неудачного старта. Каждый вывод был проверен по runtime-коду, затем исправлен отдельным RED→GREEN test; итоговые suites прошли полностью.
6. На этапе раннего прототипа с MPPM полный PlayMode-прогон обнаружил остаточный server runner между scene tests, а отдельный virtual-client test — отмену `StartGame` во время teardown. Исправление добавило ожидаемый `GameSceneController.ShutdownAsync`, ожидание незавершённого startup, idempotent teardown сцены и Unity-null проверки runner после отмены Fusion. Отмена теперь нормализуется в `OperationCanceledException`, а не публикуется как необработанная ошибка.
7. AI реализовал `NetworkSimulationSettings` с exception-based валидацией входных значений. После ручного review владелец проекта заменил её нормализацией через `Math.Max(0, value)`: отрицательные delay, jitter и probabilities больше не прерывают настройку симуляции, а приводятся к допустимому нижнему пределу. Это лучше соответствует назначению runtime-настроек debug-панели.
8. Первая реализация клиентского таймера вычисляла остаток от `serverTime` конкретного snapshot в момент его получения. При искусственной задержке это повторно прибавляло время доставки и могло раздвигать таймеры клиентов. После красных тестов схема заменена коррелированными heartbeat samples и midpoint RTT; отдельно закреплены неизвестные, просроченные и относящиеся к прошлому подключению ответы.
9. В промежуточной документации сохранилось упоминание Unity Multiplayer Play Mode, хотя финальная локальная топология уже была переведена на ParrelSync. При итоговой сверке README, package manifest и runtime-композиции терминология исправлена на основной Editor и два клона.

## Что решалось самостоятельно

- Выбор Photon Fusion и создание отдельного тестового Photon AppId.
- Решение оставить сервер отдельным peer, а не Host, чтобы пересоздание любого клиента не уничтожало авторитетный матч.
- Финальный выбор названий и границ слоёв после ручного review каждого checkpoint.
- Отказ от VContainer, R3, MessagePipe и ECS как избыточных для объёма задания.
- Политика отсутствующего игрока: матч не ставится на паузу, его ходы заканчиваются по timeout.
- Решение использовать классическое правило запрета касания кораблей и автоматически отмечать свободный контур потопленного корабля промахами.
- Решение хранить историю коммитов по системам и выполнять все commits/push вручную.
- Финальная ручная проверка интерфейса, запись видео и отзыв временного Photon AppId после проверки остаются ответственностью автора проекта.
